# PR-244 — TS-23: sincronización del modelo indoor publicado

Título sugerido: `feat(planning): synchronize official indoor models in mobile (PR-244)`

Desde Inicio, «Consultar mapas publicados» permite seleccionar sede y piso,
visualizar la geometría oficial y consultar sus destinos. La aplicación obtiene
pisos, nodos, conexiones, destinos, muros y puertas como una unidad inmutable.
Revalida al volver a la aplicación y mediante sincronización manual. Retira el
modelo visible durante la comprobación y ante errores; nunca usa un borrador ni
una copia anterior como respuesta a un fallo de red.

## Arquitectura y alcance

- Planning: dominio sin Flutter, contrato de repositorio, adaptador REST, servicio
  de aplicación, Cubit y pantalla. El cliente verifica escala, referencias,
  dimensiones, identidad de sede/versión y ETag antes de aceptar un grafo.
- Reutiliza `AuthorizedClient` y la sesión IAM. La caché vive solo en memoria,
  separada por sede; se invalida al cerrar/expirar sesión. Respuestas tardías no
  pueden sustituir la selección o versión más reciente.
- Conserva el tema Material y el refactor de `origin/develop`. No altera BLE,
  búsqueda de destinos ni el código Android del equipo.
- Este incremento consulta el modelo; no calcula rutas ni posicionamiento.
  El directorio Navigation existente sigue usando su propio contrato.
- No hay modo offline ni notificaciones push. Una nueva publicación se detecta
  al sincronizar o al regresar al primer plano. Los nombres de piso son metadatos
  descriptivos; la versión oficial identifica la revisión del grafo.

## Pruebas

La suite habitual incluye pruebas de transporte y dominio (unitarias), Cubit y
widgets. Los fixtures HTTP unitarios se identifican como tales; la prueba real
optativa no usa mocks HTTP y se ejecutó contra API y PostgreSQL aislados.

```powershell
flutter test --no-pub --concurrency=2 --reporter expanded
flutter analyze --no-pub
flutter build web --no-pub --dart-define=RUMBO_API_BASE_URL=http://localhost:8080
flutter build apk --debug --no-pub
```

Para integración real, preparar un JSON fuera de Git con `RUMBO_LIVE_TESTS: "true"`,
`RUMBO_API_BASE_URL`, `RUMBO_LIVE_EMAIL`, `RUMBO_LIVE_PASSWORD` y `RUMBO_LIVE_SITE`.
La cuenta debe administrar una sede **aislada de pruebas** con un modelo publicado.
Esta prueba crea y publica una versión sucesora y registra un visitante temporal;
no debe apuntar a datos de producción. No escribe ni registra tokens.

```powershell
flutter test --no-pub test/live/published_model_live_test.dart --dart-define-from-file=<config-local.json>
```

La prueba usa almacenamiento efímero solo para el estado local de sesión; las
peticiones IAM/Planning, el JWT y la persistencia PostgreSQL son reales.
